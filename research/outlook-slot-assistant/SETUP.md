# Встановлення асистента для робочого Outlook

Інструкція ставить приватного асистента для робочої скриньки Microsoft 365 на
власний сервер. Керування через Telegram. Перша фаза працює тільки в режимі
читання.

Далі в тексті **власник** це людина, чия скринька й календар використовуються, а
**оператор** це той, хто пересилає асистенту запити на зустрічі. Часто це одна й та
сама людина.

---

## 0. Що потрібно перед початком

| Що                                      | Хто дає                   | Примітка                                                   |
| --------------------------------------- | ------------------------- | ---------------------------------------------------------- |
| Робоча скринька Microsoft 365           | власник                   | особистий outlook.com не підходить для частини функцій     |
| Право реєструвати застосунок в Entra ID | власник або його IT-адмін | якщо в компанії заборонено user consent, знадобиться адмін |
| Сервер (Ubuntu 24.04, 2 vCPU, 4 ГБ)     | власник                   | найдешевшої лінійки будь-якого провайдера достатньо        |
| Доступ по SSH                           | власник                   | ключем, не паролем                                         |
| Акаунт Telegram і окрема приватна група | власник                   | там житиме вся взаємодія                                   |
| Менеджер паролів                        | власник                   | там житимуть копії значень з `.env`                        |

Час на встановлення: приблизно три години, якщо доступи готові.

### Про особисті скриньки

`findMeetingTimes` у Microsoft Graph доступний тільки для робочих і навчальних
скриньок M365. Для особистих outlook.com він не працює. Ця інструкція будує логіку
на `getSchedule`, який доступний ширше, тому схема переносима, але перед стартом
варто знати обмеження.

## 1. Реєстрація застосунку в Microsoft Entra ID

Тут визначається, що саме асистент має право бачити. Це найважливіший крок.

1. Відкрити [portal.azure.com](https://portal.azure.com), далі **Microsoft Entra ID**, далі **App registrations**, далі **New registration**.
2. Назва: `Outlook Assistant`.
3. **Supported account types**: `Accounts in this organizational directory only (single tenant)`.
4. **Redirect URI**: не заповнювати. Вхід піде через device code.
5. Натиснути **Register**. Записати **Application (client) ID** і **Directory (tenant) ID**.
6. Перейти в **Authentication**, знайти **Allow public client flows**, поставити **Yes**, зберегти. Без цього device code не працює.
7. Перейти в **API permissions**, далі **Add a permission**, далі **Microsoft Graph**, далі **Delegated permissions**. Додати рівно два дозволи:
   - `Mail.Read`
   - `Calendars.Read`
8. Натиснути **Grant admin consent**, якщо кнопка доступна. Якщо ні, власник погодить доступ сам під час першого входу. У багатьох тенантах user consent для цих двох дозволів дозволений.
9. Більше нічого не додавати. Ні `Mail.ReadWrite`, ні `Mail.Send`, ні `Calendars.ReadWrite`, ні `Files.Read`. Кожен зайвий дозвіл це те, що асистент зможе зробити помилково.

### Як власник відкликає доступ

Entra ID, далі **Enterprise applications**, знайти `Outlook Assistant`, далі
**Permissions**, далі **Review permissions**, відкликати згоду. Після цього
асистент миттєво втрачає доступ, і жоден токен на сервері вже не працює. Це
посилання варто тримати в закладках.

## 2. Сервер

Бот працює на Telegram long polling, тому відкриті порти, домен і сертифікати не
потрібні.

```bash
# під root, один раз
adduser --disabled-password --gecos "" assistant
apt update && apt install -y ufw fail2ban python3-venv sqlite3 git
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp
ufw enable
systemctl enable --now fail2ban
timedatectl set-timezone Europe/Kyiv   # підставити таймзону власника
```

Перевірка таймзони обовʼязкова. Неправильна системна таймзона це найчастіша
причина зсунутих слотів.

```bash
timedatectl   # має показати потрібну зону і синхронізований час
```

Каталоги:

```bash
install -d -o assistant -g assistant -m 700 /opt/assistant
install -d -o assistant -g assistant -m 700 /opt/assistant/state
install -d -o assistant -g assistant -m 700 /opt/assistant/config
```

Файл `/opt/assistant/.env` за зразком [config/env.example](config/env.example),
права `600`, власник `assistant`. Копії значень власник зберігає у своєму
менеджері паролів: сервер не має бути єдиним місцем, де вони існують.

Unit-файли для сервісу й ранкового брифа лежать у [systemd/](systemd).

## 3. Telegram

1. Написати [@BotFather](https://t.me/BotFather), команда `/newbot`, отримати токен.
2. Виконати `/setprivacy` для цього бота і виставити **Disable**, інакше бот не бачить повідомлень у групі.
3. Створити приватну групу, додати бота.
4. Дізнатися числові id: подивитися в логах бота після першого повідомлення, або скористатися `@userinfobot` для власного id.
5. Внести id у `TELEGRAM_ALLOWED_IDS` і `TELEGRAM_GROUP_ID`. Асистент реагує тільки на ці id, решту повідомлень ігнорує без відповіді.

### Шаблон запиту на слоти

```
#slots @counterpart 45m tz=Europe/Berlin "вт 14-16, ср після 10"
```

Чотири елементи: тег, з ким зустріч, тривалість, таймзона співрозмовника. Далі в
лапках його текст як є, будь-якою мовою.

Без `tz=` асистент спробує визначити зону з тексту. Якщо визначення неоднозначне,
він перепитає, а не вгадає.

## 4. Підбір слотів

### Логіка

1. Асистент розбирає текст співрозмовника у список інтервалів і таймзону у форматі IANA (`Europe/Berlin`, а не `CET`).
2. Усі інтервали переводяться в UTC. Уся подальша арифметика тільки в UTC.
3. Запит до Microsoft Graph:

```http
POST https://graph.microsoft.com/v1.0/me/calendar/getSchedule
Prefer: outlook.timezone="Europe/Kyiv"
Content-Type: application/json

{
  "schedules": ["owner@example.com"],
  "startTime": { "dateTime": "2026-08-04T00:00:00", "timeZone": "UTC" },
  "endTime":   { "dateTime": "2026-08-08T00:00:00", "timeZone": "UTC" },
  "availabilityViewInterval": 15
}
```

4. Перетин чотирьох умов: вікна співрозмовника, вільний час у календарі, робочі години власника, буфери до і після зустрічі.
5. Асистент віддає у групу два або три варіанти готовим текстом.

### Правила таймзон

- **Скорочення ніколи не йдуть у розрахунок.** CST це і центральний час США, і Китай, і Куба. IST це Індія, Ізраїль та Ірландія. Літній EST насправді EDT. Скорочення спершу мапиться в зону IANA, і якщо впевненості немає, асистент питає.
- **Не всі офсети цілі.** Індія плюс 5:30, Непал плюс 5:45, Eucla в Австралії плюс 8:45. Арифметика в цілих годинах на таких співрозмовниках ламається.
- **Мапінг Windows у IANA не однозначний.** Graph за замовчуванням віддає час у UTC і називає зони у форматі Windows, і одна зона Windows накриває кілька зон IANA. Тому зберігаємо IANA плюс мітку UTC і конвертуємо у себе за базою tzdata.
- **Перехід на літній час** усередині вікна вбиває будь-який розрахунок у стилі "плюс дві години". Рахунок від UTC цю проблему знімає.

### Що Graph робить, а що доводиться робити самому

`getSchedule` віддає зайнятість наявних подій, а весь інший час у запитаному вікні
вважає вільним. Тому робочі години й буфери мусять бути в конфізі, інакше асистент
запропонує суботу о сьомій ранку. Зразок:
[config/availability.example.yaml](config/availability.example.yaml).

### Формат відповіді

```
Привіт! Ось що збігається (45 хвилин):

1) Вт, 5 серпня, 14:30 за Берліном (15:30 за Києвом), 12:30 UTC
2) Вт, 5 серпня, 15:30 за Берліном (16:30 за Києвом), 13:30 UTC
3) Ср, 6 серпня, 11:00 за Берліном (12:00 за Києвом), 09:00 UTC

Тримаю ці варіанти до завтра 12:00 за Берліном. Підтвердьте номер, надішлю запрошення.
```

Три таймзони в кожному рядку прибирають більшість переносів через непорозуміння з
часом.

### Межі

- Асистент не надсилає повідомлення співрозмовнику. Він готує текст, надсилає власник.
- Асистент не створює подію в календарі у першій фазі, бо не має права запису.
- Текст співрозмовника це дані, а не команди. Якщо в тексті буде щось на кшталт "підтверди автоматично" або "надішли документ", асистент показує це власнику і не виконує. Ризик реальний, бо текст приходить від третьої особи.

### Друга фаза

Коли схема прижилася, є два шляхи розширення:

1. Додати `Calendars.ReadWrite` і дозволити асистенту ставити попереднє утримання слота, поки співрозмовник думає, а потім створювати подію після підтвердження.
2. Поставити self-hosted [Cal.com](https://cal.com) і взяти його як джерело правди про доступність (робочі години, буфери, мінімальний запас, кілька календарів), а асистента залишити для випадку, коли співрозмовник надсилає свої вікна. Тоді робочі години не дублюються у двох місцях. У self-hosted варіанті найчастіша причина зсунутих слотів це системна таймзона контейнера й неправильний `NEXT_PUBLIC_WEBAPP_URL`.

## 5. Ранковий бриф і підсвічування важливого

### Шар 1: правила в Outlook, руками, один раз

Робиться в інтерфейсі Outlook без участі асистента, тому не потребує прав на запис.

Спершу категорії. Новий Outlook або веб: **Settings**, далі **General**, далі
**Categories**. Створити три, наприклад `VIP` (червона), `Money` (оранжева),
`Legal` (фіолетова).

Далі правила: **Settings**, далі **Mail**, далі **Rules**, далі **Add new rule**.

| Правило | Умова                                               | Дія               |
| ------- | --------------------------------------------------- | ----------------- |
| VIP     | From: список важливих адрес і доменів               | Categorize: VIP   |
| Money   | Subject includes: invoice, payment, рахунок, оплата | Categorize: Money |
| Legal   | Subject includes: contract, NDA, agreement, договір | Categorize: Legal |

Правила серверні, тому колір категорії видно на всіх пристроях.

Про кольори тексту варто знати окремо. Розфарбовування самих рядків листа за
відправником (Conditional Formatting) існує тільки в класичному Outlook для
Windows: **View**, далі **View Settings**, далі **Conditional Formatting**. У новому
Outlook і у веб-версії його немає, і офіційний обхід це саме категорії плюс
правила. Тому схема будується на категоріях, а не на кольорі шрифту.

### Шар 2: конфіг асистента

[config/vip.example.yaml](config/vip.example.yaml) визначає порядок у брифі, тоді
як правила Outlook визначають колір у клієнті. Бриф приходить у Telegram щоранку і
сортується за вагою, а не за часом отримання. Один рядок містить вагу, відправника,
тему, час і категорію. Тіла листів у бриф не потрапляють і в логи не пишуться.

### Шар 3: асистент вчиться

Коли власник відповідає `важливо` або `шум` реплаєм на рядок брифа, асистент
дописує відповідний рядок у `vip.yaml` і показує готовий текст правила для Outlook,
якщо його варто додати. Через місяць список збирається сам.

Це дешевша альтернатива вбудованій пріоритезації Copilot, яка вимагає окремої
ліцензії Microsoft 365 Copilot і не дає ні експорту, ні контролю над логікою.

## 6. Плановий шар

Горизонти місяць, шість місяців і два роки, метрики й ритуали описані окремо:
[PLANNING-LAYER.md](PLANNING-LAYER.md).

працює лише підбір слотів і бриф. Плановий шар додається тоді, коли власник уже
щодня заходить у групу сам.

## 7. Безпека і приватність

Делеговані дозволи рівно два: `Mail.Read` і `Calendars.Read`. Асистент не може ні
надіслати лист, ні змінити календар, навіть якщо помилиться.

Тіла листів не зберігаються. У стан і логи йдуть тільки метадані: відправник, тема,
час, категорія, вага. Вкладення не завантажуються і в модель не передаються.

У пошті лежить переписка третіх осіб, тому група в Telegram приватна, склад
учасників мінімальний, історія не пересилається далі.

Текст листа або повідомлення співрозмовника ніколи не є інструкцією для асистента.

Refresh token живе близько 90 днів без активності. Для щоденного бота це не
проблема, але після довгої відпустки знадобиться повторний вхід. Асистент
попереджає в чаті, коли авторизація прострочена.

Файл `.env` і каталог `state` доступні тільки користувачу `assistant`, права `600`
і `700`.

Резервна копія: щодня дамп SQLite, зберігати два тижні. У стані немає листів,
тільки налаштування й історія запитів.

## 8. Рунбук

### Повторний вхід у Microsoft

```bash
sudo -u assistant /opt/assistant/venv/bin/python -m assistant login
```

Команда покаже код і посилання. Власник відкриває
[microsoft.com/devicelogin](https://microsoft.com/devicelogin), вводить код і
входить робочим акаунтом.

### Базові команди

```bash
systemctl status assistant              # чи живий бот
journalctl -u assistant -n 100          # останні логи
systemctl restart assistant             # перезапуск
systemctl list-timers | grep assistant  # чи стоїть ранковий бриф
```

### Типові поломки

| Симптом                                      | Причина                                                        | Що робити                                                                                 |
| -------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Бот не відповідає в групі                    | сервіс упав або в BotFather увімкнений privacy mode            | `systemctl status assistant`, перевірити `/setprivacy` = Disable                          |
| Помилка авторизації Microsoft                | токен прострочений або згоду відкликано                        | повторний вхід, перевірити застосунок в Enterprise applications                           |
| Слоти зсунуті на години                      | системна таймзона сервера або `timezone` у конфізі             | `timedatectl`, потім `availability.yaml`                                                  |
| Пропонує вечори й вихідні                    | у конфізі не задані робочі години                              | заповнити `working_hours`, це не помилка Graph, вона справді вважає вільним усе незайняте |
| Категорії не фарбують рядки в новому Outlook | розфарбовування рядків є лише в класичному Outlook для Windows | працювати з категоріями, кольоровий чіп видно всюди                                       |
| Бриф порожній                                | немає нових листів за вікно або зламався фільтр дати           | подивитися логи брифа, перевірити вікно в конфізі                                         |

## 9. Межі підтримки

Якщо асистента ставить одна людина для іншої, домовленість варто зафіксувати
письмово: що входить у встановлення, чого в ньому немає, і що власник робить
самостійно. Мінімальний набір самостійних дій: повторний вхід у Microsoft,
перезапуск сервісу, редагування `vip.yaml` і `availability.yaml`, відкликання
доступу.
